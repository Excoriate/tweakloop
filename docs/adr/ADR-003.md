# ADR-003 — SQLite plus content-addressed filesystem objects

## Status

Accepted

## Context

Tweakloop is local-first and OSS-first: it needs transactional durable state, concurrent readers, recoverability, and queryable history without a cloud service. Artifact bytes (HTML, assets) and large evidence (screenshots, logs, patches) are immutable blobs that do not belong inside database rows.

## Decision

SQLite is the fact log, using `STRICT` tables and WAL mode, accessed through `better-sqlite3` behind a narrow storage port (`transact` / `queryEvents` / `readProjection`). Its synchronous transaction model aligns with a serialized transactor. Do not make `node:sqlite` the public foundation yet — as of Node 26.5.0 it remains at release-candidate stability. Pin a maintained `better-sqlite3` release containing a patched SQLite build (SQLite fixed a rare WAL reset race, present through 3.51.2, in 3.51.3). Artifact and evidence bytes live in a content-addressed object store at `objects/sha256/ab/cd/<full-hash>`, written temp-file → flush → verify hash → atomic rename, and never overwritten. SQLite stores hash, media type, length, relationships, and metadata.

## Alternatives rejected

- Blobs inside SQLite (bloats the fact log; complicates immutable serving).
- `node:sqlite` as the foundation today (stability), though it remains the intended future driver.
- An ORM (use explicit SQL and explicit data transformations).
- Postgres/Redis/Kafka (see ADR-002).

## Consequences

The driver must never leak into the domain; replacing it stays mechanical. A missing object for a known hash is an integrity failure — never fabricate a revision. Native-module installation cost (better-sqlite3 build scripts) is accepted.

## Falsifier

Object-store scale pathologies, or `better-sqlite3` maintenance lapsing behind SQLite security fixes.

## Migration path

Swap the driver (e.g. to a stabilized `node:sqlite`) behind the storage port; the object store layout is driver-independent.
