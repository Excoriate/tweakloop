# ADR-009 — Semantic IDs and explicit orphaning

## Status

Accepted

## Context

Agents routinely regenerate documents, so raw DOM paths and CSS selectors are too fragile to carry feedback across revisions. Silently reattaching feedback to a merely similar element corrupts what the human meant — a worse failure than losing the anchor visibly.

## Decision

Durable anchors are semantic: `data-tweak-id` (meaning, not presentation — `architecture.data-storage`, never `left-card-3`), with `data-tweak-kind` and `data-tweak-source` alongside. An anchor record preserves independent clues: revision ID, semantic ID, source reference with line ranges, text quote with prefix/suffix context, a DOM hint, and an `anchorStrength`. Re-anchoring against a newer revision tries, in order: exact semantic ID → explicit source reference → uniquely matching text quote with context → normalized structural path → orphan. Orphaning is an explicit durable fact (`artifact.anchor-orphaned`) surfaced to the human, who can retarget, dismiss, delegate to an agent, or keep the feedback artifact-level. Markdown identity derives deterministic IDs from heading ancestry and block role, retaining parser source positions; a content hash alone is never identity.

## Alternatives rejected

- CSS selectors or DOM paths as durable identity (locators, not identities).
- Content hashes as semantic identity (they change precisely when content changes).
- Silent best-match retargeting (forbidden by the no-silent-recovery law).

## Consequences

Adapters must build a semantic index per revision. An anchor-health projection reports which targets remain valid. Producers (agents) must be taught to emit stable IDs; the vertical slice depends on it.

## Falsifier

If producers in practice never emit stable semantic IDs, orphaning becomes the common case and the anchor model degenerates to text-quote matching.

## Migration path

Re-anchoring heuristics can strengthen behind the same anchor record shape; new clue fields are additive.
