# ADR-006 — Versioned command, event and bridge schemas

## Status

Accepted

## Context

Protocols are data. Browsers, CLIs, and arbitrary agent harnesses integrate across versions and restarts; exposing internal TypeScript classes as the protocol couples every consumer to implementation churn and makes old data unreadable.

## Decision

Every public surface is a versioned data schema validated at the boundary:

- **Commands**: one envelope (`tweakloop.command/v1`) carrying `commandId`, `idempotencyKey`, `workspaceId`, `actor`, `type`, `expected.streamVersion`, and a payload validated against the schema for `type`.
- **Events**: the `STRICT` events table records `seq`, `event_id`, `workspace_id`, `stream_type`, `stream_id`, `stream_version`, `event_type`, `schema_version`, `recorded_at`, `actor_json`, `causation_id`, `correlation_id`, `payload_json`, with `UNIQUE (workspace_id, stream_id, stream_version)` for optimistic concurrency.
- **Bridge messages**: `tweakloop.bridge/v1` envelopes with sequence numbers; unknown major versions are rejected.
- **CLI output**: `tweakloop.cli/v1` — one documented JSON value on stdout, diagnostics on stderr, stable exit codes.
- **Manifests and evidence**: `$schema`-tagged JSON (revision manifests, intent payloads, evidence envelopes).

## Alternatives rejected

- TypeScript types as the de facto protocol.
- Unversioned payloads.
- Destructive event migrations (superseded by readers/upcasters in projection code).

## Consequences

A schema registry lives under `protocol/`; JSON Schema validation runs at every boundary. Old protocol data remains readable after additive evolution (architecture invariant 17). Slightly more ceremony per new command or event type.

## Falsifier

If Tweakloop only ever has one co-versioned client and the schema overhead never pays for itself.

## Migration path

Additive fields within a version; upcasters for old schema versions; a major protocol bump for breaking changes, with both majors served during transition.
