# ADR-011 — POST commands plus SSE notifications

## Status

Accepted

## Context

The shell needs to submit durable mutations and observe committed changes; agents need to wait for claimable work. Full-duplex WebSocket state is more connection machinery than this command/notification shape requires, and long-polling as a coordination model ties the durable queue to process liveness.

## Decision

Commands travel as ordinary POSTs to `/api/v1/commands`. Committed updates flow over one server-sent-events connection per shell (`GET /api/v1/events?after=<seq>`), with SSE event IDs equal to durable database sequences. No event is published before its transaction commits. On reconnect the browser resumes from its last observed sequence; the daemon replays later committed events; if the gap is too large or incompatible, the browser fetches a fresh projection snapshot. One SSE connection serves the whole shell — never one per artifact iframe. `tweak work claim --wait` may hold a long-lived request internally, but the durable queue never depends on the waiting process staying alive.

## Alternatives rejected

- WebSocket as the default transport (full-duplex state without a proven bidirectional requirement).
- Long-polling as the central coordination model (effective transport in prior art, wrong durability model).
- Per-iframe event connections.

## Consequences

Replay and reconnect semantics are trivial because ordering is the database `seq`. Browser reducers consume the same committed events that projections do. The transport is inspectable with plain HTTP tooling.

## Falsifier

A proven bidirectional streaming requirement that POST plus SSE cannot satisfy.

## Migration path

Add a WebSocket channel alongside SSE if the falsifier occurs; the committed-event envelope and sequence semantics remain unchanged.
