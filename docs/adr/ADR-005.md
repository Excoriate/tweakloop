# ADR-005 — Separate trusted shell and artifact origins

## Status

Accepted

## Context

Agent-generated HTML is untrusted application content: arbitrary JavaScript, third-party libraries, forms, links, media, malformed markup, accidental or intentional requests. Injecting a privileged SDK into that document, on the same origin as the review UI and its credentials, gives artifact code a path to the shell DOM and mutation APIs.

## Decision

The daemon runs two loopback HTTP listeners on OS-assigned ports: a **shell origin** (trusted UI, command API, authentication, SSE stream) and an **artifact origin** (read-only immutable revision files plus the versioned bridge script — no POST routes, no shell cookie). Artifacts render in a sandboxed iframe (`sandbox="allow-scripts allow-same-origin allow-forms allow-modals allow-popups allow-downloads"`, `referrerpolicy="no-referrer"`); `allow-same-origin` is acceptable only because the origins are separate and the artifact server has no privileged endpoints. The shell establishes communication with an exact-origin `postMessage` handshake — validating `event.origin`, `event.source`, protocol version, and payload schema, never targeting `"*"` — then transfers one `MessageChannel` port, which becomes the sole bridge capability.

## Alternatives rejected

- Single origin with iframe sandbox alone (credentials and DOM reachable on escape).
- Injecting the SDK directly into the artifact document as the trusted surface.

## Consequences

Bootstrap authentication (one-time token → HttpOnly SameSite=Strict cookie), Origin/Host/CSRF validation, and a DNS-rebinding host allowlist are required on the shell origin. Playwright security tests must prove the artifact cannot read shell DOM or call mutation APIs.

## Falsifier

A demonstrated isolation escape, or a review capability that genuinely requires shell-origin access from artifact code.

## Migration path

Sandbox permissions become capability-driven per artifact; LAN or public binding requires a separate future security design.
