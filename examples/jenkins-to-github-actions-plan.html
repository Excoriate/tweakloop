Migrating CI from Jenkins to GitHub Actions

Plan for review, revision 1. The thesis: migrate build shapes, not jobs — and delete more than you translate.

Overview and strategy

The trap. The obvious plan is "translate every Jenkinsfile into a workflow." It fails predictably: most Jenkins estates are a long tail of near-duplicate jobs plus a minority of scripted Groovy pipelines that are genuinely programs. Translating one-to-one reproduces a decade of accumulated workarounds in a new syntax, and the team inherits the same mess with worse tooling familiarity.

The plan instead. Three moves, in this order:

  1. Cull. A large fraction of Jenkins jobs have not run in a year. They are not migration scope, they are deletion scope. This is the cheapest work in the whole programme and it shrinks everything downstream.
  2. Collapse. The surviving jobs almost always reduce to a handful of archetypes — service build, library publish, container image, infrastructure apply. Build one well-made reusable workflow per archetype and most repositories become a ten-line caller file.
  3. Rewrite the remainder by hand, with the owning team, against those reusable workflows. No automated Groovy transpilation — see decision.no-auto-transpile.

Sequencing constraint. Runner and identity foundations (Phase 2) gate everything else. A workflow that cannot reach an internal artifact repository or authenticate to the cloud is not a migrated job, and no amount of YAML quality fixes that. Nothing beyond a pilot moves until Phase 2 is real.

Shape of the effort. Phase 1 inventory and cull (~3 weeks) → Phase 2 runners and identity (~6 weeks, the critical path) → Phase 3 golden-path workflows (~4 weeks, overlaps Phase 2) → Phase 4 migration waves (~2 quarters, distributed across owning teams, not a central factory) → Phase 5 per-repo cutover (continuous) → Phase 6 Jenkins decommission (~4 weeks, gated on a hard date). Roughly two platform engineers for three quarters, plus a few days per repository from each owning team.

Assumptions this plan rests on

These are guesses about your estate, written down so they can be corrected rather than silently baked in. Each one changes the plan materially if wrong — replace any that are inaccurate.

Scale. On the order of a few hundred Jenkins jobs across one Jenkins controller (or a small number of controllers), with somewhere between a third and a half of them effectively dead.
Composition. A mix of declarative Jenkinsfile pipelines, some legacy Freestyle jobs configured through the UI, and at least one Groovy shared library that most pipelines depend on.
Network. Builds need access to internal services — an artifact repository, private package registries, possibly a database for integration tests — that are not reachable from GitHub-hosted runners.
Source of truth. The code already lives in GitHub (or is being moved there independently). This plan covers CI only; it does not cover repository migration.
Deployment. Jenkins does some production deployment, not just build and test. If Jenkins is build-only, Phase 2's identity work and Phase 5's approval mapping shrink dramatically.

Phase 1 — Inventory and cull read-only

Extract a machine-readable inventory of every job from the Jenkins API (/api/json?tree=jobs[...], plus config.xml per job) and turn it into a table the platform team and each owning team can argue with.

Per job, capture:

FieldWhy it matters
Type — Freestyle / declarative Pipeline / scripted Pipeline / Multibranch / Matrix / Maven / Job DSL-generatedDetermines translation difficulty; Job DSL means the job is generated and the generator is the real migration unit

Plugins referenced by the job's stepsPlugin usage is the best predictor of translation cost

Disposition, assigned to every job: delete (dead or superseded), fold (fits an archetype, becomes a reusable-workflow caller), rewrite (real logic, needs a human), or keep-on-jenkins (out of scope for now, with a named reason and a review date). Every job gets exactly one, and no job is allowed to be absent from the report.

Also inventory the plugins themselves. A plugin-usage histogram across the estate is the single most useful artifact from this phase: it tells you which five plugins to solve properly (and how) and which forty are used once each and can be handled ad hoc.

Exit criteria: every job has a disposition and an owner; the delete set has actually been disabled (not yet deleted — disabled, so reversal is one click); the plugin histogram is published; the cross-job dependency graph is drawn.

Phase 2 — Runner and identity foundation critical path

This is the phase that actually determines whether the migration succeeds, and the one most plans under-resource because it produces no visible migrated jobs.

Runners

Jenkins agents are typically long-lived VMs sitting inside the network with ambient access to everything. GitHub Actions runners are ephemeral and, if GitHub-hosted, outside the network entirely. Three options, and most estates need a mix:

OptionUse forCost shape
GitHub-hosted runnersAnything that only needs the internet — most builds, linting, unit tests, public dependenciesPer-minute; no ops burden
Self-hosted via Actions Runner Controller (ARC) on KubernetesBuilds needing internal network access; large or specialised hardwareYour compute + real ops burden; ephemeral pods per job
GitHub-hosted larger runnersBuilds that are slow purely for CPU/RAM reasonsHigher per-minute, no ops burden — often cheaper than it looks against engineer wait time

The design decision is in decision.runner-strategy. Whatever the mix, agent labels need an explicit mapping to runner groups and labels, and that mapping should shrink: Jenkins label sprawl is usually historical accident, not requirement.

Identity and secrets

Jenkins credentials are encrypted in the controller's store and can technically be decrypted by an administrator. Do not do that. Migrate names and consumers, not values:

  • Produce a secret inventory: credential id, type, which jobs consume it, and a proposed GitHub home (organisation secret, repository secret, or environment secret).
  • Prefer eliminating the secret over moving it. Every cloud credential that can become OIDC federation should — this migration is the best opportunity you will get to delete long-lived cloud keys, and doing it now costs less than doing it as a follow-up project that never gets scheduled.
  • Humans re-provision the values that remain, directly in GitHub. The migration tooling never reads a secret value.
  • Package registry and artifact repository access moves to short-lived tokens or OIDC where the registry supports it.

Exit criteria: a pilot repository builds and deploys end to end on the new runners using the new identity model, with no credential copied from Jenkins.

Phase 3 — Golden-path reusable workflows

Build a small, well-maintained set of reusable workflows (on: workflow_call) in a dedicated .github-style platform repository, one per archetype identified in Phase 1. A migrated repository should usually end up with a caller file of roughly ten lines.

Typical archetype set: service build-and-test, library build-and-publish, container image build-and-push, infrastructure plan-and-apply, and a static-site or docs build. Adjust to what the inventory actually shows — this list is a hypothesis, not a finding.

Each reusable workflow carries the things you do not want re-litigated per repository: dependency caching, test result and coverage publishing, artifact retention, required permissions scoped down from the default, SBOM and provenance if applicable, and consistent job naming so branch protection rules stay stable across repos.

Shared libraries. The Jenkins Groovy shared library is the piece with no clean equivalent, and it needs a deliberate decomposition rather than a translation:

Shared library contentGitHub Actions home
Whole-pipeline templates (buildJavaService())Reusable workflow
Reusable step sequencesComposite action
Real logic — parsing, computation, API callsA checked-in script (or a TypeScript action) with its own tests, called from a step
Shared constants and configurationOrganisation variables, or a config file in the platform repo
Groovy that exists to work around JenkinsDeleted

That last row is usually larger than anyone expects, and finding it is a good use of the first rewrite.

Supply-chain hygiene from day one: third-party actions pinned to commit SHAs, an organisation allowlist of permitted actions, permissions: declared explicitly at workflow level, and GITHUB_TOKEN defaulted to read-only across the organisation. These are one-time settings that are painful to retrofit after two hundred workflows exist.

Phase 4 — Migration waves

Migration is delegated to owning teams with platform support, not performed centrally. A central factory becomes the bottleneck and, worse, produces workflows nobody feels responsible for.

  1. Pilot (2–3 repositories). Chosen for representativeness rather than ease: one straightforward service, one that deploys to production, one that is awkward. The awkward one is the point — it is what calibrates the estimate for everything else.
  2. Wave 1 — the fold set. Jobs that map onto an archetype. These should take hours, not days, each. If they do not, the golden paths are wrong and Phase 3 needs another pass before the wave continues.
  3. Wave 2 — the rewrite set. Scripted pipelines and genuinely bespoke jobs, done with the owning team, scheduled explicitly rather than squeezed in.
  4. Wave 3 — the stragglers. Unowned jobs, jobs whose owners have left, jobs everyone is afraid of. Handle these by switching them off and seeing who complains, in a window where that is safe. It sounds glib; it is faster and more accurate than archaeology, and the disable-then-restore path makes it cheap to be wrong.

Support model: a migration guide with a worked example per archetype, a dedicated chat channel, and standing office hours. Track progress on a single public dashboard — jobs migrated, jobs remaining, by team. Visible progress is what keeps a long tail moving.

Phase 5 — Per-repository cutover

Cutover happens per repository, not as a flag day, and runs in three steps with a different rollback at each:

  1. Shadow. Both systems build every push. Jenkins remains the required status check; the Actions workflow reports but cannot block a merge. Rollback is free. Stay here for an agreed number of green runs rather than an agreed number of days — a repository that builds twice a week needs more calendar time than one that builds forty times a day.
  2. Gating swap. The required status check moves to the Actions workflow; the Jenkins job keeps running but stops gating. Rollback is a branch-protection change, measured in minutes.
  3. Retirement. The Jenkins job is disabled, not deleted, and stays that way through the soak period. Rollback is re-enabling it.

Parity, not vibes. Before a repository leaves shadow mode, compare the two systems on evidence: same exit status across the shadow window, same produced artifact names, test counts within tolerance, and a build-duration comparison. Differences are usually real findings, not noise.

Two honest limits. Shadow mode double-executes side effects — two builds may both push an image tag, both write to a shared integration environment, or both send notifications. Every job with an external side effect needs a per-job decision: run shadow with deploy and publish steps stubbed, or skip shadow for that job and accept a sharper cutover. And rollback covers CI configuration only; an artifact published or a deployment made by a bad run is outside the rollback path and stays the team's problem.

Approvals change shape, mostly for the better. A Jenkins input step blocks a running build and often an executor with it; the equivalent is a GitHub Environment with required reviewers, which gates a job without holding a runner. Behaviour differs enough to be worth calling out to teams during their cutover: timeouts, who can approve, and what happens on rejection are not the same.

Phase 6 — Jenkins decommission

An un-decommissioned Jenkins is a migration that did not happen. Two systems means double maintenance, double patching, and a permanent escape hatch back to the old world.

  • Set the shutdown date at the start of Phase 4, publicly, and treat it as a real constraint. A date set at the end is a date nobody planned around.
  • Read-only first. Jenkins goes read-only (no new builds, history browsable) for a defined period before shutdown.
  • Decide what happens to build history before you need it: which jobs have retention obligations, and whether history is exported to an archive or the controller is snapshotted as a VM image that can be revived if an auditor asks. This is a compliance question, not an engineering one, and it needs an owner outside the platform team.
  • Reclaim what it was using — agent VMs, controller hosts, licences, plugin subscriptions. This is the number that justifies the programme in a budget conversation, so measure it.

Key decisions

No automated Jenkinsfile-to-workflow transpilation

Tools exist that convert Jenkinsfiles to Actions workflows. This plan does not use them as the primary path. Declarative pipelines are regular enough that conversion is mostly mechanical — and mostly unnecessary, because those are exactly the jobs that should collapse into a golden-path caller instead. Scripted Groovy pipelines are Turing-complete programs; converting them produces workflows that are syntactically valid, semantically approximate, and unmaintainable by the team that has to own them.

What we do instead: classify in Phase 1, fold what fits an archetype, rewrite what does not, and use conversion tooling only as a reading aid for an engineer who is writing the real workflow.

What this costs: more human hours in Phase 4 than a transpile-everything approach appears to need, and the appearance of slower early progress. The trade is that the resulting workflows are ones their owners understand.

GitHub-hosted by default; self-hosted only where the network requires it

Default to GitHub-hosted runners, and treat every self-hosted runner as a cost with a justification attached. Self-hosted capacity is provisioned through Actions Runner Controller with ephemeral pods, never long-lived VMs — the persistent-agent model is what makes Jenkins agents drift and what makes them a security problem.

Why not lift the agent fleet across: reusing the existing agent VMs as self-hosted runners is tempting and fast, and it carries the entire drift problem into the new system while giving up ephemerality, the main safety property Actions offers.

The real constraint is which builds genuinely need internal network access. Phase 1's inventory answers that, and it is usually a smaller set than teams assume — much of what looks like an internal dependency is a package registry that has a public mirror or a proxy.

Teams own their workflows; the platform team owns the golden paths

The platform team builds and maintains reusable workflows, runners, and the migration guide. Owning teams migrate their own repositories against those. The platform team pairs, reviews, and unblocks — it does not migrate on other teams' behalf except for genuinely unowned jobs.

Why: a central migration factory hits a throughput ceiling immediately, and workflows written by someone else become nobody's responsibility the first time they break at 2am. The counter-argument — that this is slower and less consistent — is answered by the golden paths carrying the consistency, not by the migrator.

Re-provision secrets; federate wherever possible

No credential value is exported from the Jenkins credential store. Names, types, and consumers migrate; humans provision values into GitHub organisation, repository, or environment secrets. Every cloud credential that can be replaced by OIDC federation is replaced during migration rather than deferred.

Consequence to plan around: this makes cutover blocking on humans in a way a copy would not, so the secret inventory has to be produced early (Phase 2) and tracked as its own work queue, with cutover for a repository refused while any of its secrets are outstanding.

Risks

The Groovy shared library is the long pole high

If most pipelines import a shared library, no repository can fully migrate until the library's capabilities exist on the Actions side. It is a single point of coupling across the whole estate, and it is usually under-documented and maintained by one or two people.

Mitigation: decompose it in Phase 3 (see the mapping table there) before Wave 1 rather than discovering its shape mid-wave; start from the functions the inventory shows are actually called, which is typically a small fraction of what the library exposes; and treat deleting Jenkins-workaround code as a goal of the exercise rather than a loss of fidelity.

Builds that quietly depend on a persistent workspace high

Jenkins agents reuse workspaces between builds. Some builds are incremental, fast, or even correct only because of state left behind by the previous run — a populated dependency cache, a built container layer, a generated file nobody remembers generating. Actions runners start clean every time. These failures appear as "works on Jenkins, fails on Actions" with no obvious cause, and they are the most common source of frustration early in a migration.

Mitigation: flush them out early by running the pilot jobs on Jenkins with a clean workspace before migrating, which reproduces the failure in the system the team already understands. Then handle the real dependency explicitly with actions/cache or a build cache service — as a declared input, not an accident.

Self-hosted runners with network access are a serious attack surface high

A self-hosted runner that builds pull requests will execute code from those pull requests inside your network. Combined with a non-ephemeral runner, this is a well-understood path to persistence and lateral movement, and the migration is exactly when it gets introduced by accident.

Mitigation: ephemeral runners only (one job per pod, never reused); self-hosted runners never attached to public repositories; pull_request_target treated as a reviewed exception rather than a convenience; runner network egress and identity scoped to what the build needs rather than inherited from the old agent VMs; and runner groups restricting which repositories can schedule onto which pools. Decide these before the first self-hosted runner exists — retrofitting them means auditing every workflow.

Compute cost becomes visible, and visible cost reads as new cost medium

Jenkins compute is usually buried in an infrastructure budget nobody itemises. Actions minutes arrive as a line item, and the first invoice can trigger a reaction out of proportion to the actual change — especially where matrix builds got copied across without anyone asking whether every combination is needed.

Mitigation: baseline current Jenkins compute spend during Phase 1 so the comparison is available before it is demanded; model expected minutes from real build durations during the pilot; set concurrency limits and path filters in the golden paths so pushes do not trigger unnecessary work; and present the Phase 6 decommission savings alongside the new cost rather than months later.

Build numbers and artifact versioning discontinuity medium

Jenkins BUILD_NUMBER is monotonic per job and frequently ends up embedded in artifact versions, image tags, or release names. github.run_number starts at 1 for a new workflow, which can produce version numbers that go backwards — and downstream systems that resolve "latest" by version ordering will do something surprising and hard to diagnose.

Mitigation: identify affected jobs in Phase 1 (search for BUILD_NUMBER in the inventory); prefer moving those to semantic versions or commit-SHA tags during migration, which is the better end state anyway; and where continuity is genuinely required, add a fixed offset so numbering continues past the Jenkins high-water mark.

Cross-job dependencies break in the middle of the migration medium

Jobs that trigger other jobs, or copy artifacts from them, only work if both ends are on the same system — or if someone bridges them. A repository migrated in Wave 1 whose downstream deploy job is still on Jenkins is a broken pipeline, and the breakage lands on whoever pushes next rather than on the migrator.

Mitigation: the Phase 1 dependency graph drives wave composition — connected components migrate together, not repository by repository. Where a component is too large to move at once, bridge deliberately (repository_dispatch from Jenkins, or a Jenkins job triggered by a workflow) with the bridge tracked as scheduled debt with a removal date, never as an unplanned improvisation.

The long tail stalls medium

The failure mode for this kind of programme is not technical: it is eighty percent migration, no shutdown date, and two CI systems forever. Teams migrate the repositories they touch daily and leave the rest, and the residual Jenkins keeps the escape hatch open indefinitely.

Mitigation: the public shutdown date from Phase 6 set during Phase 4; a visible per-team dashboard; disabling rather than migrating anything nobody will claim; and executive agreement up front that the date is real, obtained while the programme is still popular rather than when it is behind.
