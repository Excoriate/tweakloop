01 · MVP at a glance

Prove four things. Ship nothing to production.

The POC is deliberately narrow: one exporter path, representative traffic, two operator views, and a reversible failure test. The output is a go / extend / stop recommendation—not a migration.

proposed decision

Run a shadow POC. Keep InfluxDB authoritative.

Use one VPPAL exporter to dual-write a bounded workload. Compare the stored facts and two representative dashboards. Break the candidate on purpose. Stop after four gates produce a decision.

The smallest useful implementation

1
Freeze the baseline

Choose one exporter, one representative workload window, and two dashboards. Record current Influx results.

2
Deploy the candidate

Provision one private Flexible Server, enable TimescaleDB, and create the minimum schema and fail-open writer.

3
Run in shadow

Dual-write for the agreed window. Compare facts, freshness, query results, and the two operator views.

4
Break it, then decide

Block PostgreSQL, prove VPPAL keeps running, restore service, price the footprint, and record go / extend / stop.

02 · Evidence boundary

Four labels prevent one polished falsehood.

Each technical claim belongs to one proof class. The distinction is part of the design because vendor support, source structure, and operational readiness answer different questions.

Open evidence rules
source vendor proposed unknown gate

source Repository-declared fact

Observed in the bounded VPPAL evidence packet: caller counts, exporter topology, measurement names, dashboard count, fail-open behavior, deployment surfaces, and placement ownership.

vendor Microsoft-documented capability

Azure documents the TimescaleDB Apache-2 extension and its activation shape on Flexible Server. The cited pages remain specifications until the target server is probed.

proposed POC mechanism or threshold

A candidate design chosen to produce evidence: bounded buffering, schema variants, private access, test thresholds, migration stages, and operator drills.

unknown Decision-blocking gap

No live Azure, OpenShift, Argo, Grafana, InfluxDB, PostgreSQL, or pipeline surface was queried for the source packet. These gaps become owned gates in this design.

Proof ceiling. Source inspection proves the current integration shape. Microsoft Learn proves a vendor-documented activation contract. Only target-environment experiments can prove activation, performance, failure isolation, recovery, cost, and operational ownership. Only a human decision can approve migration.

The storage port is narrow; the migration surface is not.

Thirteen business-flow callers depend on a storage-neutral port, but seven applications, ten point mappers, secret delivery, deployment configuration, dashboards, and the self-managed Influx lifecycle bind the operating system to InfluxDB.

04 · Candidate architecture

Isolate the experiment at the exporter boundary.

The candidate keeps the thirteen callers stable, fans monitoring records into independent sinks, and prevents PostgreSQL latency, connection pressure, or outage from becoming business-path backpressure. Every orange element is a proposal to test, not an implemented fact.

Open architecture detail

Fail-open writer contract

Primitive: a monitoring fact emitted after domain processing.

Transformation: a non-blocking or strictly bounded enqueue copies it to the candidate path; the background writer batches records with finite connection and statement timeouts.

Invariant: candidate queueing, retries, logging, and telemetry consume bounded time and memory; no exception or pressure propagates into operational processing or the Influx sink.

Consequence: database loss causes visible monitoring loss, not VPPAL control loss. The cost is accepted sample loss during candidate failure; the experiment must quantify it.

05 · Workload, data model & query mapping

Preserve contracts before optimizing tables.

The source packet names measurements but not complete tag/field schemas, cardinality, row width, or live rates. The POC must inventory those facts first, then compare a contract-preserving nine-hypertable baseline against a consolidation by stable grain.

Open data and query detail

Option A · nine hypertables

Keep one typed table per current measurement. It maximizes semantic traceability and gives every exporter an obvious target, at the cost of repeated columns and more policy objects.

Option B · stable-grain families

Consolidate compatible pool- and device-grain facts behind typed views. It can reduce schema and query repetition, but only if field sparsity and retention semantics do not create a braided generic table.

Control · generic JSON payload

Use only as a negative control. It can ingest unknown shapes quickly while hiding type drift, index cost, query semantics, and governance—the exact questions the POC must answer.

proposed Retention and downsampling ladder

Raw window: retain raw samples for the owner-approved troubleshooting period. Downsampled window: preserve only aggregates whose exact query semantics are proven against raw fixtures. Expiry: remove data through an owned, observable policy or scheduled job. The POC must verify which TimescaleDB policies/functions exist in the activated Azure extension version; it must not infer them from generic Timescale documentation.

Gate: before any deletion test, record current Influx retention, legal/governance requirements, dashboard lookback, ad-hoc needs, and restore interaction. Until then, no target retention number is approved.

06 · Provisioning, activation, security & networking

A database resource is the first dependency, not the migration.

Terraform should own the managed service lifecycle; Helm/GitOps should own workload configuration. The POC proves the seam between them, including private reachability, extension activation, credentials, restart behavior, and evidence export.

Open provisioning detail

Confirm canonical owner and target environment

source Current source-declared placement is Eneco.Vpp.Aggregation.Infrastructure for Sandbox and Eneco.Vpp.Aggregation.Infrastructure.Mc for MC dev/acc/prd, unless live inventory identifies a shared-service owner.

Provision an isolated server on the approved private path

proposed Define server, database, approved private connectivity, DNS, TLS enforcement, monitoring export, backup configuration, tags, budget attribution, and explicit public-ingress denial. Validate the actual network mode and region/SKU combination in Azure.

Allowlist the TimescaleDB extension

vendor Flexible Server requires an extension to be allowlisted before creation. Record the exact server parameter, PostgreSQL major version, and TimescaleDB version returned by the target.

Add the library and restart deliberately

vendor Microsoft documents adding the library to shared_preload_libraries; the parameter is static, so the server must restart. Capture availability impact and configuration parity after restart.

Create and inventory the extension

vendor A database owner creates the extension in the target database. Capture SELECT extversion, available functions, licensing edition, and a minimal hypertable creation probe; revoke owner privileges from runtime roles afterward.

Deliver runtime configuration to seven apps

proposed Extend the existing Key Vault → CSI → Kubernetes Secret pattern or an approved identity alternative. Roll out per application; verify endpoint, database, role, certificate mode, pool limits, sink mode, and kill switch without embedding credentials in Helm or logs.

Database roles

  • Owner/admin: platform-controlled, no application use.
  • Migrator: schema and policy changes only in deployment window.
  • Writer: insert/batch privileges on target tables; no DDL.
  • Grafana reader: select on approved views; no raw secret/config access.
  • Comparator: time-bounded read access to raw POC data.

Network and transport

  • No public application ingress; prove with positive and negative connectivity tests.
  • Private DNS resolves from every participating workload namespace.
  • TLS verification is mandatory; reject plaintext and invalid certificate paths.
  • Egress is restricted to the approved server endpoint and port.
  • Server logs and metrics export to a plane that survives database failure.

07 · Migration, dual-write & rollback

Cut over authority in steps; never move data and trust in one motion.

Dual-write is an experiment instrument, not proof by itself. It must isolate failures, assign identity to comparisons, and expose whether differences come from writer loss, time-window semantics, dashboard translation, or retention.

Open migration and rollback detail

Baseline · Influx-only authority

Inventory active endpoints, bucket policy, all writer shapes, actual rates/cardinality, Grafana panels/variables/alerts, and operational performance. Freeze deterministic test windows and fixtures.

Synthetic replay · candidate isolated

Replay known records into PostgreSQL without touching application traffic. Prove activation, schema, query semantics, retention mechanics, and comparator accuracy, including deliberately corrupted controls.

Shadow write · Influx authoritative, PostgreSQL observed

Enable the bounded candidate sink on one low-risk application, then expand by explicit wave. Compare complete time windows only after allowed lateness; inject PostgreSQL failure before adding the next workload.

Shadow read · duplicated dashboards, no operator authority

Run translated Grafana dashboards beside the current versions. Compare panel values, gaps, freshness, latency, variables, alert behavior, and ad-hoc tasks without changing operational links.

Reader authority · PostgreSQL dashboards, Influx safety net

Only after acceptance gates pass, switch an explicitly scoped reader cohort while dual-write continues. Restore Influx dashboards immediately if parity, freshness, or operations regress.

Writer authority · candidate primary, Influx reversible

Requires a separate human decision record. Keep the Influx deployment, configuration, and re-enable path intact for the agreed soak; verify rollback from an injected candidate outage.

Retirement · supersede, then remove

Decommission only after live-consumer inventory, retention/export obligations, rollback soak, cost, support ownership, and restore evidence close. Archive evidence and explicitly accept any historical data not migrated.

Dual-write can look safer while increasing blast radius. A synchronous fan-out, shared connection budget, unbounded retry queue, or log storm can make candidate failure slow the authoritative path. The failure-injection gate must black-hole the database, exhaust its pool, force restart, and deny credentials while business traffic continues.

possible outcome

Continue to migration proposal

All X-01…X-12 gates pass, remaining risks have named owners, and a human records a new decision. This POC design alone cannot produce that outcome.

possible outcome

Extend the POC

A bounded unknown can change the decision and has a specific probe, owner, timebox, and no production dependency. Thresholds are not relaxed merely to make a result green.

possible outcome

Stop / no-go

Fail-open, query semantics, security, recovery, upgrade, cost, or ownership cannot meet the accepted gate. Influx remains authoritative; evidence is retained for future alternatives.

13 · MVP run sequence

Four checkpoints; stop as soon as the route is invalid.

Duration follows access and evidence—not a calendar promise. Each checkpoint has one useful output and one explicit stop condition.

Baseline

Select one exporter, one workload window, and two dashboards; freeze thresholds and owners. Output: replay bundle + current results. Stop if: no safe boundary or accountable owner.

Candidate

Provision one isolated private server; activate TimescaleDB; create the smallest typed schema and bounded writer. Output: reproducible deployment. Stop if: activation, network, or security fails.

Shadow test

Dual-write the bounded workload; compare facts and two dashboards; measure freshness; black-hole PostgreSQL. Output: parity + failure evidence. Stop if: VPPAL behavior regresses.

Decision

Restore the candidate, price the measured footprint, and record go / extend / stop. Output: one-page recommendation with evidence links. Stop after this: production migration requires a separate decision.

14 · Decision record

Record what is decided—and what is deliberately still open.

These entries govern the POC. Any change requires a superseding record with evidence and impact; prose edits must not silently move a gate.

Open decision records
DR-01 · proposed

Run a bounded POC; make no replacement commitment.

Enables: evidence under real constraints. Prevents: architecture-by-vendor-capability. Costs: temporary dual infrastructure and engineering time.

DR-02 · inherited constraint

Preserve fail-open functional monitoring.

Enables: safe fault injection. Prevents: database failure becoming VPPAL control failure. Costs: accepted, observable monitoring loss under outage.

DR-03 · proposed

Use isolated dual-write and shadow reads.

Enables: deterministic comparison and reversible reader cutover. Prevents: big-bang authority transfer. Costs: duplicate writes, temporary complexity, and a new comparison identity problem.

DR-04 · proposed

Compare contract-first and stable-grain schemas.

Enables: evidence-based schema choice. Prevents: premature generic-table optimization. Costs: two synthetic implementations before one is retired.

DR-05 · constraint

Do not decommission InfluxDB inside the POC.

Enables: rollback and honest no-go. Prevents: evidence collection from becoming irreversible migration. Costs: the POC cannot claim lifecycle savings until a later soak.

DR-06 · evidence rule

Keep vendor, activation, workload, and owner proof separate.

Enables: claim-safe decisions. Prevents: source or documentation checks laundering runtime readiness. Costs: more gates remain visibly open.

Final authority. The POC team supplies evidence and a recommendation. The named human decision owner accepts, extends, or rejects the migration proposal. Passing technical tests does not automatically authorize production cutover.
