Scope

What v0 must do

v0 is a local developer tool, not a Git server. It orchestrates worktrees inside an existing repository checkout.

CommandPurposeNotes
wt listShow all worktrees with branch, path, dirty stateDefault human table; --json for scripts
wt add <name>Create a worktree under a convention pathDefault: ../<repo>-<name> on a new branch wt/<name>
wt remove <name>Remove worktree and optionally delete branchRefuses if dirty unless --force
wt pruneRemove stale worktree registrationsMaps to git worktree prune + orphan detection
wt cd <name>Print path for shell integrationeval "$(wt cd foo)" or direnv hook later

The finish line

What success means

v0 is done when an agent or human can spin up an isolated worktree, do work, and tear it down without touching the main checkout.

  1. Fast listing

    wt list --json returns stable fields in <200ms on a repo with 10 worktrees.

  2. Safe creation

    wt add feature-x creates path + branch; rerunning fails clearly instead of corrupting state.

  3. Clean removal

    wt remove feature-x refuses dirty trees; --force documented with explicit risk.

  4. Scriptable output

    Every command supports --json with schema-stable keys for automation.

Smallest credible path

The plan

Four phases. Each phase ships a usable command before moving on.

  1. Phase 1 — Scaffold

    Cargo binary wt, clap CLI, --json output helper, integration test harness invoking real git in a temp repo.

  2. Phase 2 — Read path

    Implement list and cd by parsing git worktree list --porcelain plus porcelain status for dirty detection.

  3. Phase 3 — Write path

    Implement add and remove with naming conventions, idempotency checks, and actionable error messages.

  4. Phase 4 — Hygiene

    Implement prune, stale-worktree warnings in list, and shell completion snippets.

Open implementation detail

Stack: Rust 2021, clap (derive), serde/serde_json, anyhow/thiserror for errors. No libgit2 in v0 — shell out to the installed git binary for correctness and to avoid linking complexity.

Layout: Single crate at repo root or tools/wt/. Modules: cli, git (command runner), model (Worktree struct), output (table vs JSON).

Config: Optional .wt.toml later; v0 uses flags only. Defaults: worktree parent directory = sibling of repo root; branch prefix = wt/.

Tests: End-to-end tests in tests/ using tempfile + real git init/worktree operations. CI runs on Linux and macOS.

Why not the alternatives?

Shell scripts / Just recipes: Fast to start but brittle for JSON output, error handling, and cross-platform path logic. Good for prototypes, poor for agent consumption.

Python CLI: Fine DX, but Rust gives a single static binary, stronger typing for output contracts, and matches a performance-sensitive tooling direction.

libgit2 / gitoxide: More control, but worktree edge cases and parity with CLI behavior add scope. Revisit if shell-out becomes a bottleneck.
