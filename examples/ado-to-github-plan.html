adoport — migrating Azure DevOps project configuration to GitHub

Implementation plan, revision for review. Target: a single CLI that moves the configuration around a repository, not the repository itself.

Overview and scope

Problem. GitHub Enterprise Importer (gh ado2gh) moves git history, pull requests and work items, but it deliberately leaves behind everything that makes a project build and ship: pipelines, variable groups, service connections, environments and branch policies. Teams migrate the code in an afternoon and then spend six weeks hand-rewriting CI. adoport closes that gap.

Shape. A gh CLI extension (gh extension install org/adoport) written in Go, so it ships as a single static binary and runs unchanged on a laptop or in CI. It authenticates as its own app identity rather than borrowing the operator's gh credential — see decision.auth-model. Three verbs mirroring Terraform: adoport inventory (read-only), adoport plan (translate + diff), adoport apply (mutate GitHub).

Roughly one engineer-quarter to a usable v0.1, gated on the corpus coverage number in risk.pipeline-semantic-gaps.

Phase 1 — Inventory read-only

Crawl an ADO project through the REST API (api-version=7.1) and produce a normalised, provider-neutral model. Nothing is written to GitHub in this phase, so it is safe to run against production on day one.

  • Sources: build/definitions, release/definitions (on vsrm.dev.azure.com), distributedtask/variablegroups, distributedtask/environments, serviceendpoint/endpoints, policy/configurations, distributedtask/taskgroups, and secure files.
  • Output: inventory.json (the durable model every later phase reads) plus a human-readable inventory.md.
  • Disposition per object: every discovered object is classified auto, assisted or manual. This classification is the tool's core honesty mechanism — it is what turns "we migrated your project" into a number a lead can argue with.
  • Classic vs YAML: definitions carry process.type (1 = designer, 2 = YAML). Designer pipelines have no YAML source and must be reconstructed from the JSON task graph; they are never classified better than assisted.

Exit criteria: inventory round-trips against a fixture project in CI, and every object type above has at least one disposition rule. No object may be silently absent from the report.

Phase 2 — Pipeline translation

The heart of the tool. Parse azure-pipelines.yml with a schema-aware parser, resolve template: includes (including cross-repo templates declared under resources.repositories), expand parameters, then lower the result onto the Actions workflow schema.

Task mapping catalog. Task translations live in versioned YAML data files, not in Go code, so the long tail can be extended by contributors without a release. Each entry pins the target action to a commit SHA and declares an input mapping plus a confidence level.

Unmapped tasks fail loudly. When no catalog entry matches, the emitted step is a run: exit 1 placeholder carrying the original task inputs as a comment. A migrated workflow that has not been finished must never go green — a silently no-op deploy job is the worst possible failure mode for this tool.

Phase 3 — Variable groups, secrets and service connections

Constraint. The CLI never reads, exports, or copies secret values. Only secret names and metadata migrate; humans re-provision values in GitHub environments. Rationale: secret material must never transit the migration tool.
  • Non-secret variables map directly to Actions variables. A group referenced by one pipeline becomes repo-level; a group shared across pipelines becomes org-level with selected-repository visibility.
  • Secret variables migrate as names only. The ADO API returns isSecret: true with a null value anyway, so the constraint above costs us nothing on plain variable groups: adoport creates the secret name and emits secrets-todo.csv listing every secret a human must populate, with the pipelines that consume it.
  • Key Vault-backed groups are re-linked, not read. An earlier draft proposed reading values straight out of Key Vault when the operator had data-plane access. The constraint rules that out, and the replacement is better: the vault reference migrates instead of the value, so the translated workflow fetches the secret from Key Vault at run time using the OIDC identity from the migrated service connection. The value never lands in a GitHub secret at all, and rotation in Key Vault keeps working exactly as it did in ADO.
  • Azure service connections become OIDC. Rather than copying a client secret, the tool adds a federated credential to the existing app registration through Microsoft Graph (subject: repo:ORG/REPO:ref:refs/heads/main, and one per environment), then writes AZURE_CLIENT_ID, AZURE_TENANT_ID and AZURE_SUBSCRIPTION_ID as variables. No long-lived credential is created or moved. Registry and generic connections fall back to secrets with a TODO entry.
  • ADO environments with approval checks map to GitHub Environments with required reviewers and wait timers; the reviewer identity mapping comes from a user-supplied identity-map.csv (ADO UPN → GitHub login), since there is no reliable automatic join between the two directories.

Phase 4 — Repo policies to rulesets

ADO policies are discovered by type GUID from policy/configurations and lowered onto repository rulesets rather than legacy branch protection, because rulesets support org-level definition, layering and explicit bypass actors — the forward-compatible target.

Phase 5 — Dry run, apply, verify, cut over

  • Plan/apply. adoport plan writes a reviewable plan file; adoport apply executes it. Dry run is the default; --yes is required for mutation.
  • Everything additive. Repository content (workflows, CODEOWNERS) is delivered as a pull request, never a direct push to the default branch. Rulesets, variables and environments are created, never overwritten, unless --adopt is passed.
  • Parity check. adoport verify dispatches each translated workflow on a scratch branch and compares the result against the last N ADO runs — exit status, produced artifact names, wall-clock duration — so the team sees evidence rather than a claim.
  • Cutover. ADO pipelines are disabled (queueStatus: disabled), not deleted, and the project stays readable for an agreed soak period. adoport revert undoes GitHub-side resources using the state file.

Q. What is the rollback path if pipeline translation fails validation after cutover — do teams dual-run ADO and GitHub pipelines for a window?

Yes, dual-run is the default and the plan was under-specified here. Cutover is not one switch but three, and the rollback path is different at each step:

  1. Shadow (both run, GitHub non-gating). Both systems build every push. ADO remains the required status check on the branch policy; GitHub Actions runs alongside and reports, but cannot block a merge. Rollback is free — nothing depends on the new workflows yet. This is where adoport verify's parity comparison collects its evidence, over an agreed number of green runs rather than an agreed number of days.
  2. Gating swap (both run, GitHub gating). The required status check moves to the GitHub workflow and the ADO build validation policy is relaxed to optional. ADO still builds. Rollback is a single adoport revert --step gating, which restores the ADO policy from the state file and drops the GitHub ruleset back to its previous revision; the window is minutes, and no repository content changes.
  3. Retirement (ADO triggers disabled). Only entered on an explicit command after step 2 has been stable for the soak period. Because pipelines are disabled rather than deleted, rollback is re-enabling queueStatus and re-pointing the branch policy — also one command.

The reason for three steps rather than a flag day: a translated pipeline usually fails on something environmental — a missing secret, a self-hosted runner label, a subscription the OIDC identity cannot reach — and those failures only appear against real workloads. Shadow mode surfaces them while ADO is still authoritative, which is the whole point of the exercise.

Two honest limits. Dual-run double-executes side effects: two builds may both push a container tag or both write to a shared integration environment. The tool cannot detect this automatically, so adoport plan flags every step it classifies as externally-effecting and requires the team to decide per pipeline whether shadow mode is safe, or whether the GitHub side runs with deploy steps stubbed. And rollback covers configuration only — artifacts published or deployments made by a bad GitHub run are outside the tool's state file and stay the team's problem.

Key decisions

Authentication: app and workload identity, never personal access tokens

Authenticate to GitHub with a GitHub App installation (OIDC where possible); authenticate to ADO via an Entra ID service principal. Personal access tokens are forbidden on both sides.

What this costs us. The tool no longer piggybacks on whatever credential the operator happens to have in gh auth, so a migration now has a setup step: install the App on the target repositories and grant the service principal read access to the ADO project. That is a real friction increase on day one, and it is the right trade — an operator's personal token carries their whole blast radius into an automated bulk-mutation tool, and the audit log would attribute every ruleset change to a person who was not making the decision.

Permissions required. GitHub App: Administration (rulesets), Actions variables and secrets, Environments, Contents and Pull requests (the workflows PR). ADO service principal: read on Build, Release, Task Groups, Variable Groups, Service Endpoints and Policy. Both are read-only on the ADO side by construction — the tool's only ADO write is disabling pipeline triggers at cutover.

Token handling. App installation tokens live one hour, which is shorter than a large migration, so the tool refreshes on demand and never caches a token to disk. In CI it runs under a federated workload identity with no stored credential at all. A redaction layer sits in front of all logging and plan-file serialisation; any value sourced from a secret field is replaced with its digest before it can reach disk or stdout.

A deterministic transpiler, not an LLM

Translation is a data-driven, deterministic lowering pass over a typed intermediate representation. The same input always produces byte-identical output, which makes golden-file tests possible and makes review diffs meaningful across tool versions. An LLM in this position would be unreviewable at exactly the moment review matters most — a deploy step.

The concession: an opt-in --explain flag may use a model to describe an unmapped task in the TODO comment. It never emits executable YAML.

Stateful plan/apply with a resource map

A state file (.adoport/state.json, committed or stored alongside the migration) maps each ADO source object id to the GitHub resource created from it. This buys idempotent re-runs, partial and resumable migrations, and a working revert. The alternative — a stateless tool that diffs live GitHub against live ADO on every run — cannot distinguish "not migrated yet" from "deliberately deleted after migration", which is the case that matters during a multi-week cutover.

Risks

Constructs with no clean Actions equivalent high

Task groups, deployment jobs with rolling and canary strategies, gates and pre-deploy checks, and extends templates used as an organisational policy mechanism have no faithful one-to-one mapping. Translation quality is therefore a distribution, not a boolean.

Mitigation: fidelity tiers reported per step; the exit 1 placeholder rule from Phase 2; and a published coverage number measured against a corpus of real pipelines collected before GA. Ship the number honestly — a tool that claims 100% and delivers 70% costs more trust than it saves time.

Migration is inherently partial because secrets cannot be read high

The dangerous shape here is a workflow that is green because it authenticated against nothing, or a deploy that silently targets the wrong subscription because a variable was migrated but its secret counterpart was not.

Mitigation: adoport verify secrets asserts the presence of every required secret before cutover is allowed, and the cutover command refuses to disable ADO pipelines while any entry in secrets-todo.csv is outstanding.

Quietly weakening controls during a compliance-relevant migration medium

Rulesets are not a superset of ADO branch policies (see the gaps in Phase 4). In a regulated org, silently dropping "work item linking required" is an audit finding, not a papercut.

Mitigation: every apply emits a control parity report enumerating each policy that could not be reproduced, and the run fails unless the operator passes --accept-gaps — an explicit, logged act of acceptance rather than a default.
